# ADR-004：插件暂存注册、清单校验和统一装配入口

状态：本次阶段 6 实现采用。

## 背景

配置加载不能直接修改正在运行的 CLI，否则插件注册一项后抛错会遗留半加载状态。代码装配也不能直接调用 activate 绕过校验。加载器属于宿主，不应通过导入表或条件分支识别具体插件。

## 决策

- 所有插件以 `Plugin` 的类实例为默认导出。清单来自各插件包的 package.json，`contributes` 只有 shapes、commands、decorators、attributes 四类，缺省视为空集合。
- `PluginLoader.load` 为两种装配的共同入口：新建独立 PluginContext，等待同步或异步 activate 完成，按类别和名称集合比较声明/实际注册，最后由宿主 `installExtensions` 提交。
- 插件只得到暂存上下文，不得到宿主 application。清单不匹配或激活抛错时，暂存上下文被丢弃，实际解析器、图形工厂和运行注册表不改变。
- 提交前对全部注册项进行契约检查及四类别冲突预检（包含默认命令和六种内置图形），预检通过后同步发布。当前启动加载严格串行，因此提交期间没有并发加载穿插。
- 同类名称重复拒绝整个当前插件，打印规定的 duplicate registration 错误。之前成功的插件保留，后续插件仍继续。
- 配置先整体解析/校验再执行任何插件，数组顺序即加载顺序；enabled=false 不解析、不导入、不激活。options 作为第二个参数原样传递，插件自行解释，不由加载器添加私有字段。
- 相对模块名以配置文件目录为准；包名用该目录为起点的 Node createRequire.resolve 规则查找入口，再以 ESM import 执行。插件的 package.json 从入口向上寻找；各示例包提供 main=index.ts，由项目的 tsx 运行环境执行。本地包不需要发布或安装到市场。
- 先解析顶层模块，再导入。只有顶层解析的 MODULE_NOT_FOUND 输出 plugin not found；已找到入口后的求值、依赖、清单及 activate 错误输出 failed to activate，避免把缺失依赖误报为顶层模块不存在。
- 无效/不可读配置只打印 invalid plugin config，保持默认内置能力启动，不偷偷启用代码装配中的可选插件。

## 边界

这里的原子性仅覆盖框架注册状态，不是对第三方 JavaScript 的安全隔离；插件自行执行网络/文件 IO 或修改模块外部状态，框架不能自动回滚。契约要求 activate 只构造实例并登记能力。配置仅加载可信插件。

本次工作不重写已推送的阶段 2—5 历史。新增接口、加载器和接入修正会体现在将来的阶段 6 提交；老师要求的“接入新插件时不修改旧运行代码”的 A/B 独立提交证据应在后续演示提交中单独完成，不能仅凭当前双装配输出相同就宣称满足 Git 差异判据。
